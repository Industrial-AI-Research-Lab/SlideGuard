# System Overview

## General Overview

SlideGuard is an automated evaluation system for slide-based presentations that leverages large language models (LLMs) to provide structured, multi-criteria feedback. Given a PDF presentation and a declared presentation type (scientific, industrial, collaborative, or technological), the system produces per-slide and per-deck assessments across a configurable set of quality criteria, accompanied by an aggregated score, a natural-language summary, and an exportable PDF report.

The system operates at two levels of granularity. At the **slide level**, each slide is rendered as a raster image and independently assessed by vision-capable LLMs against criteria such as visual arrangement, orthography, title–content coherence, abbreviation usage, and type-specific requirements (e.g., scientific novelty or industrial applicability). At the **deck level**, textual descriptions generated during slide-level analysis are aggregated and evaluated for narrative structure, storytelling quality, and research rigor. This two-level design reflects the distinction between local slide quality and global presentation coherence, and enables the system to surface both fine-grained issues and structural deficiencies.

SlideGuard is built on LangGraph for workflow orchestration and LangChain for LLM interaction, and is compatible with both OpenAI API endpoints and self-hosted inference servers (e.g., vLLM). The evaluation pipeline, criteria definitions, and output schemas are fully decoupled, allowing new criteria to be introduced through configuration alone without modifying the core evaluation engine.

## Graph-Based Evaluation Pipeline

The evaluation pipeline is implemented as a directed acyclic graph (DAG) using LangGraph's `StateGraph` abstraction. The graph is assembled dynamically at invocation time based on the selected criteria and comprises three sequentially dependent subgraphs.

The first phase executes **service criteria** in parallel: a slide type classifier assigns each slide one or more semantic labels from a predefined taxonomy (e.g., "Title slide", "Problem Statement", "Experimental Results"), while a description generator produces a structured textual summary of each slide's content, layout, and visual elements. Both service criteria operate on slide images via multi-modal LLM prompts and are prerequisite to all subsequent evaluation steps.

The second phase launches two concurrent subgraphs. The **slide-level subgraph** evaluates each non-service criterion in parallel across all applicable slides. Before evaluation, an applicability filter restricts each criterion to eligible slides based on the classified slide types, the declared presentation type, and optional constraints such as the presence of infographic content. Slides that do not match a criterion's applicability rules receive a "not applicable" marker and are excluded from scoring. Each criterion node constructs a LangChain prompt chain, queries the LLM with the slide image, and parses the response into a typed Pydantic model via a structured output parser with retry logic. The **deck-level subgraph** operates concurrently: it aggregates all per-slide descriptions into a single textual representation of the presentation and evaluates deck-level criteria (storytelling, structure analysis, research quality) against this aggregated text input.

The third phase is the **summary subgraph**, which executes sequentially after both slide-level and deck-level evaluations complete. A summary processor filters and prioritizes the collected findings using adaptive severity thresholds, then prompts the LLM to generate a long-form summary and a condensed TL;DR. Finally, an overall score is computed as the mean of all individual criterion scores.

Parallel branches within each subgraph share state through LangGraph's annotated merge mechanism: custom reducer functions (`_merge_dicts`, `_merge_lists`) combine partial outputs from concurrently executing nodes into a single coherent `EvaluationState` object. This approach ensures deterministic merging regardless of node completion order.

## Configurable Criteria Framework

The criteria system follows a registry pattern that separates criterion definition from evaluation logic. Each criterion is specified declaratively as a `CriterionConfig` instance, which encapsulates: a unique identifier, a target level (slide or deck), a system prompt template (which may be a static string or a function of the presentation type), a task prompt template, an output specification, applicability constraints, a priority value, a category label, and an optional list of post-processor functions.

Output schemas are generated programmatically at registry initialization time. Most evaluation criteria use the `scored_list` output kind, for which the framework dynamically constructs a Pydantic model via `create_model` containing a list of scored items (each with severity, detected element, and actionable suggestion fields) and an overall integer score. This auto-generation eliminates boilerplate while ensuring that every criterion produces a structurally consistent, machine-readable output. Criteria with non-standard output formats (such as the service criteria for slide type classification) declare a `custom` output kind and supply a hand-written Pydantic model.

Applicability constraints enable fine-grained control over which criteria apply to which slides. A criterion may declare a whitelist or blacklist of slide types, a whitelist or blacklist of presentation types, and a flag indicating that infographic content is required. These constraints are evaluated at runtime against the slide type classifications produced by the service criteria, ensuring that, for example, title slide quality assessment runs only on title slides and graphic-content match assessment runs only on slides containing infographics.

Post-processor functions provide a composable mechanism for refining LLM outputs after parsing. The current implementation includes severity-based filtering and sorting, domain-specific whitelisting (e.g., suppressing known abbreviations like institutional acronyms), and deduplication with aggregation (e.g., combining multiple abbreviation findings on a single slide into one consolidated item). Post-processors operate on the typed criterion result objects and are applied in the order specified in the criterion configuration.

Adding a new evaluation criterion requires only appending a `CriterionConfig` to the configuration list and defining the corresponding prompt. The evaluation engine, caching layer, and user interface automatically discover and incorporate the new criterion without code changes to any other module.

## Caching and Infrastructure

The system employs a two-level caching architecture to minimize redundant computation. The **file-level cache** stores the results of PDF-to-image conversion: each uploaded presentation is hashed (SHA-256 over file content), and the extracted slide images are persisted in a content-addressable directory structure. Subsequent evaluations of the same file reuse the cached images without re-rendering.

The **evaluation cache** stores per-criterion results keyed by a composite identifier comprising the presentation file path, the criterion identifier (augmented with the presentation type and output language), the slide index, and a content hash of the input entity (the slide image path for slide-level criteria, or the serialized deck description for deck-level criteria). Results are serialized with Python's `pickle` protocol. Notably, the cache distinguishes between successful evaluation results and fallback results produced by error recovery: fallback objects carry a sentinel marker and are never persisted, ensuring that a failed evaluation is automatically retried on the next invocation rather than served from cache.

Cache key construction incorporates the presentation type and the selected output language as suffixes to the criterion identifier, guaranteeing that evaluations performed under different type contexts or language settings do not collide. This design enables safe reuse of cached results even when a user re-evaluates the same presentation with a different subset of criteria, since each criterion's cache is independent.

The LLM integration layer wraps LangChain's `ChatOpenAI` with a `ControlledLLM` class that addresses several practical concerns of deploying structured output parsing against heterogeneous LLM backends. Structured output extraction uses a `PydanticOutputParser` with format instructions appended to each prompt, followed by a multi-attempt retry strategy: if initial parsing fails, a `RetryWithErrorOutputParser` re-prompts the LLM with the parsing error, and a final fallback attempts direct JSON deserialization with text normalization. Language control is implemented by injecting explicit language directives into every prompt, enabling per-evaluation switching between English and Russian output without model fine-tuning. For slide-level criteria, the system embeds slide images as base64-encoded data URIs within multi-modal chat messages, enabling compatibility with any OpenAI-compatible vision API including locally hosted vLLM instances.
